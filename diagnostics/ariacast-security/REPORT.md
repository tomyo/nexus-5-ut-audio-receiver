# AriaCast privacy and security audit

**Scope:** static source review of AriaCast Android repository, commit `0eab0c28c87549b1b657854087df21820a511349` (2026-10-22), plus the checked-in AriaCompanion firmware. No app code, phone settings, or running services were changed. This report cannot establish which APK is installed or what packets were observed on the phone.

## Verdict

I found **no source evidence of covert telemetry or automatic upload of captured audio to an AriaCast-controlled Internet service**. The only compiled-in Internet API destinations found are GitHub's release-check and plugin-catalog APIs. Normal capture is deliberately streamed to the receiver selected by the user.

That is **not** a guarantee that the audio stays only on the selected receiver: active streaming opens unauthenticated local-network listeners, optional third-party plugins have access to raw audio and arbitrary networking, and some companion/protocol features have serious local-network trust gaps. Treat the app as a trusted LAN audio-capture tool, not as a network-isolated recorder.

## Must fix / avoid on untrusted networks

1. **Any reachable network peer can fetch live captured PCM during DLNA/Cast streaming** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/AudioCastService.kt:794-805,831-879`). The app binds a wildcard TCP socket on port `8091`; each accepted client receives the live audio flow without authentication, destination/path validation, or source restriction. The URL is intentionally given to the selected receiver, but it is not restricted to that receiver. The stream uses HTTP and adds `Access-Control-Allow-Origin: *`. Anyone able to route to the phone on that port while this listener is active can listen to the same audio. It closes at session cleanup (`:2016-2024`). **Smallest fix:** restrict serving to the selected receiver(s), use an unguessable per-session URL/token, and do not emit permissive CORS; ensure the socket binds only on the intended interface if feasible.

2. **The AriaCompanion board's LAN API allows persistent audio redirection without authentication** (`/var/home/tomyo/projects/ariacast-android-audit/AriaCompanion/AriaCompanionWifiBridge/src/api_server.cpp:34-136`; port/advertisement in `src/api_server.h:20` and `src/main.cpp:71-83`). In particular, `POST /api/receiver` changes the destination saved in NVS and redirects future audio; `/api/status` exposes Wi-Fi SSID/IP and current target; `/api/wifi/reset` clears credentials and reboots to setup. The handlers enable permissive `Access-Control-Allow-Origin: *` (`api_server.cpp:12-16`). This applies **only if you use the companion board**, not ordinary direct casting. **Smallest fix:** authenticate mutations/status with a secret established at provisioning, validate origin as defense in depth, and require an explicit physical reset for re-provisioning.

3. **Companion Wi-Fi provisioning sends the home Wi-Fi password over HTTP through an open setup AP** (`/var/home/tomyo/projects/ariacast-android-audit/AriaCompanion/AriaCompanionWifiBridge/src/wifi_setup.cpp:95-116`; Android sender `app/src/main/java/com/aria/ariacast/AriaCompanionActivity.kt:189-223`). The setup AP has no password and accepts `/save`; the phone POSTs `ssid` and `pass` to `http://192.168.4.1/save`. A nearby listener during setup can capture the home PSK. Firmware stores it in NVS (`src/config_store.h:26-51`). Applies only when provisioning/using the companion. **Smallest fix:** use authenticated encrypted provisioning (or avoid sending the home credential through this board); at minimum make setup AP time-limited and protected with a per-device credential.

4. **Optional plugins can deliberately exfiltrate raw audio and other app capabilities** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/PluginManager.kt:266-297,460-474,492-557`). An enabled plugin receives the Activity, Context, AudioCastService and DiscoveryManager; the `onAudioBuffer` event gives it each captured PCM buffer, and the `http.post` / `ws.request` helpers accept arbitrary URLs. The Rhino class restrictions are not an OS security boundary: the source itself says plugins can call public methods on injected objects (`:33-49`). This is disclosed by an explicit plugin-system consent prompt (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/res/values/strings.xml:131-132`) and an enableable plugin is not the same as secret app telemetry. Only enable plugins you trust as much as the app. Plugin sync fetches catalog files from GitHub and disables changed enabled scripts pending review (`PluginManager.kt:607-657`). **Mitigation:** leave plugins disabled unless needed; inspect each script and updates before enabling. For a real sandbox, redesign around narrow capability objects and OS process isolation rather than relying on Rhino.

## Should fix / know the limits

5. **AirPlay DACP remote control accepts a request with no token** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/airplay/DacpServer.kt:97-125`). It rejects a *wrong* `Active-Remote` value, but only checks when the header exists; a missing header reaches play/pause/volume command handling. The endpoint binds a wildcard port and is advertised over mDNS while AirPlay is active (`AudioCastService.kt:1229-1269`). A peer on the reachable network can manipulate playback/volume during that session. Existing test coverage always sends a token and only tests a foreign one (`/var/home/tomyo/projects/ariacast-android-audit/app/src/test/java/com/aria/ariacast/airplay/RtpAudioSenderTest.kt:189-210`). **Fix:** require an exact matching token and add a missing-header test.

6. **AirPlay RTP retransmission can send buffered audio packets to any requester** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/airplay/RtpAudioSender.kt:358-395`). While streaming, the UDP control loop accepts retransmit requests without checking the sender against the selected receiver and replies to the request's address/port. This exposes retained packets in supported unencrypted modes and can amplify spoofed LAN traffic; encrypted AirPlay modes limit the confidentiality impact. **Fix:** accept control packets only from the selected receiver's address/port and rate-limit the response.

7. **A tapped `ariacast://` link can start casting to its supplied host without an in-app destination confirmation** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/AndroidManifest.xml:76-95`; `app/src/main/java/com/aria/ariacast/MainActivity.kt:268-320`). A malicious link can point to an attacker's receiver; optional `ssid`/`pass` parameters can offer a network to Android's system add-network flow (`WifiJoinManager.kt:14-39`). This is user-triggered, and Android's MediaProjection prompt is still required, but that prompt does not identify the receiver. A Wi-Fi password embedded in such a URI/NFC tag is readable by anyone who can read the tag (`NfcWriteActivity.kt:181-208,224-232`). **Mitigation:** do not open untrusted casting links or scan unknown setup tags; show the resolved host prominently and require confirmation before capture.

8. **AirPlay pairing secrets labelled “secure” are stored in ordinary private SharedPreferences** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/AudioCastService.kt:289-290,2213-2237`). Android's app sandbox protects these in normal operation and backup rules exclude `AriaCastSecurePrefs.xml` (`app/src/main/res/xml/data_extraction_rules.xml:7-14`), so this is a hardening issue against rooted/forensic access, not evidence of remote leakage. Consider Android Keystore-backed encryption and verify the file remains excluded from backup.

9. **The app logs the current track title and playback position** (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/MediaNotificationListener.kt:165-174,235-245`). Logs are local Android logs, not an upload path found in source, but apps with privileged log access / debugging tooling may read them. Avoid sharing logcat output without checking/redacting it.

## What looks intentional / reassuring

- Audio capture uses Android MediaProjection and `AudioPlaybackCaptureConfiguration` limited to `USAGE_MEDIA` (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/AudioCastService.kt:658-677`); it is not microphone capture. Android/app playback-capture policy can still exclude individual apps.
- Video/screen casting is off by default (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/SettingsActivity.kt:134`).
- Stopping a session stops/releases `AudioRecord`, stops MediaProjection, cancels the local stream/artwork servers, and closes their sockets (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/AudioCastService.kt:1983-2024`).
- The fixed update check calls GitHub's releases API (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/UpdateManager.kt:31-36`); plugin catalog sync calls GitHub (`PluginManager.kt:615-645`). In checked source I found no Firebase, crash reporter, analytics SDK, or audio upload endpoint. This is static evidence, not a network capture.
- Audio sent directly over protocols is intentionally addressed to the selected receiver. Some protocols, notably the generic AriaCast `/audio` WebSocket, use plaintext on the transport (`/var/home/tomyo/projects/ariacast-android-audit/app/src/main/java/com/aria/ariacast/AudioCastService.kt:1455-1463`); use a trusted network. This is distinct from an automatic Internet upload.
- Artwork server on port `8090` also binds all interfaces and has no authorization (`AudioCastService.kt:317-345`), exposing the current artwork to reachable peers while the service is alive. Lower impact than live audio.
